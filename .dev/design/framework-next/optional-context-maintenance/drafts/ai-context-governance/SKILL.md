# AI Context Governance

Design specimen for #352, not installed/registered. At implementation, the entry
keeps the purpose/operations and routes to package-local references/maintenance.md;
the method below becomes that reference. No source policy/upgrade engine is needed.

## Entry and operations

Use propose for reviewable changes; apply for actually authorized bounded edits.
Obtain the problem/direct request, named files, ownership, relevant authority and
intended behavior. Audit, assessment, workflow and other skills are not prerequisites.
This optional instruction package has no config, store, executable, schema or
skill dependency; it needs an instruction reader and permitted project access.

## Propose method draft

1. Read selected owner statements, current bytes, sources and actual authority.
   Separate managed core/projections, custom content and install/recovery state.
   Unknown ownership/precedence remains unresolved for the affected action.
2. Produce before/after text or a bounded edit description with intended behavior,
   source/decision binding, applicability, alternatives and unresolved decisions.
   Preserve project meaning; do not force framework defaults. Path changes do not
   prove semantic equivalence.
3. State affected files and useful checks. Follow caller formatting/tracking; chat
   unless export requested. No automatic adoption, provider action or new ledger.
4. If useful and selected, prepare a semantic Lesson/ADR/promotion candidate for
   its public contract. Do not create all three, invent hashes or call private code.

## Apply method draft

1. Establish actual authority for the concrete radius. Already-authorized edits
   need no new permission ritual. A proposal/config/schema/actor string alone
   grants nothing. Resolve missing semantic decisions before the affected write.
2. Check ownership, relevant current contents/links and concurrent changes. Edit
   only accepted project-owned files and direct references within scope. Preserve
   unrelated work. Core, projections, locks, selection/version and recovery go to
   the selected source/installation owner; no silent radius expansion.
3. Keep full adopted rule text and required decision references with their existing
   project owner. No duplicate catalog/ledger/packet or shadow entry. Preserve
   proposal/adoption/effect distinctions. Never create another tool's adoption or
   effect evidence to make its observation pass.
4. Read back edits and run narrow authorized project checks. Report actual paths,
   outcomes, uncertainty and next actions. Diff/commit is not independent review,
   runtime effect or provider acceptance. Interrupted multi-file editing has no
   generic atomicity; report remaining state and preserve external changes.

## Optional handoff and absence draft

Read the receiving installed version's public operations and requirements when
selected. Its owner produces real queries, identities/digests and observations
under actual task authority. No private imports or implicit config/install.
Missing capability/runtime retains the candidate with handoff not executed.
Actual returned record identity is separate from acceptance/adoption/effect.

Auditor absence does not block a selected edit. Independent assessment is required
only by actual project/task authority. Unselected maintenance does not block feature,
review or knowledge work. Source release, global catalogs, framework-wide wrapper
generation, legacy migration/finalization, installation and M01 stay with their
separate owners.
