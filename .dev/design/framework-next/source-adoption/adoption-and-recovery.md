## Quiescent activation window

1. Before the window, record real fixed source/candidate/engine identities and
   exact desired managed inventory, project routing/config/template changes and
   old recovery obligations. Preview all-old drift (including unchanged files),
   unowned same-byte collisions, unknown preservation and removals. Do not assign
   new ownership merely because destinations are empty in this task's checkout.
2. Establish separate durable source/project backups below. Prepare only explicitly
   authorized project-owned roots/templates/config. Capture selected raw hashes or
   expected absence as `protected_inputs`; that byte guard does not inspect data
   semantics, discover stores or back up project data. No broad data scan.
3. Disable affected capabilities at the project level and stop affected Codex/Claude
   sessions, tools, watchers and external writers. Record who maintains quiescence
   through activation. Already-loaded instructions are not controlled by a marker.
   Unaffected work cannot modify selected managed/project inputs. Caller declarations
   are assertions, not OS attestation of all writers.
4. Resolve any active legacy upgrade/apply recovery with its **original** engine and
   owner first. A new maintenance engine cannot read/resume F07 formats. If M01 is
   actually assigned, perform/recover its exact pair separately while affected use
   stays disabled. Then recompute the managed plan against the current inputs.
5. Use #359's actual API/bootstrap under its maintenance-writer OS exclusion and
   fresh quiescence declaration. It must capture durable complete managed before/
   after bytes, old/new lock and three candidate metadata documents; immutable
   operation and identical marker precede managed mutation. Stage changed bytes,
   perform full read-back, publish matching lock and remove marker last. No-op
   cannot allocate missing coordination. Never break a held lock by deleting guard.
6. Project owner applies only reviewed root pointer/legacy-discovery retirements,
   attributes/ignore/config changes in the same window. There is no atomic
   transaction across Git, config, managed files and stores. Track intermediate
   failure and keep use disabled. Installer consistency never flips project readiness.
7. Run separately selected project public-reader observations on actual installed
   resources and intended project inputs. Reconcile missing data, unsupported old
   formats, actual template/decision bindings and any failures. Record owner decision
   to activate only after required observations succeed; installer continues to say
   `project_readiness=not-assessed`. Start fresh sessions against actual new entries.
8. Commit the coherent managed and project changes under the later authorized
   adoption task. Preserve actual candidate/development identity, backups and recovery
   records. Coordinator handles authorized online integration; clone readiness needs
   actual byte/config/data observations, not just a successful commit.

If a prerequisite is unknown, keep the affected capability inactive or on its
verified pre-window route without beginning mutation. Never silently choose another
filesystem, writer, profile, model, permission or old engine.

## Separate backup and rollback owners

| State | Durable capture before change | Restore authority and limit |
| --- | --- | --- |
| Product source and selected engine | Coherent commits reachable from durable refs/object database; exact final engine raw hashes/closure and host prerequisites | Source owner recreates matching checkout/engine; managed snapshot is not a source checkout backup |
| Project AGENTS/translations/CLAUDE/index/routes/attributes/ignore | Exact prior tracked commit plus separately saved authorized uncommitted changes, if any | Project owner restores selected files after fresh drift/ownership read; no whole-repository reset |
| Project/local config, custom templates and decision/effect inputs | Exact selected files, bytes/digests, original bindings and evidence provenance; ignored/local files need explicit external backup | Project owner, or selected M01 owner for its exact pair only; do not overwrite newer/unknown edits or invent decision evidence |
| Project records and external/ignored stores | Explicit store/file scope, versions, bindings and durable before-data when affected; new writes after activation require continued backup | Record owner checks previous-reader compatibility or reconciles forward; Git tracks only committed bytes, not everything in a RAM store |
| Managed core/runtime/lock | #359 immutable operation, exact before/after managed closure and metadata in explicit durable recovery root | Same-engine bound recovery while its operation is active; full RAM loss reconstructs only wholly missing managed content at original binding |
| Active old upgrade/apply transaction | Original engine, checkpoint/journal/receipts and its own recovery set | Original legacy owner must complete/recover; new installer cannot convert or discard it |

Before activation, a failed changed operation keeps affected use disabled: recover
managed state with its exact active operation/pin, then separately reconcile project
routes/config/data to the matching captured state. If no mutation occurred and the
old state is intact, the owner can end the window on the old route after appropriate
checks. Preserve partial results, residue and unknown/newer edits; never call a
partial restore complete.

After any use, rollback is a **new** maintenance window and fresh plan to the actual
previous candidate, not replay of a completed operation. Check newly written data
against the previous public readers. Lesson 0.1 cannot be assumed to read v2 records
or config 2. No reverse converter/compatible reader/acceptable backup means stop
and choose forward repair or explicit reconciliation. Do not discard new records
to manufacture an apparently successful rollback; there is no invented stable base.

On complete F: loss, managed reconstruction alone is insufficient. Restore source,
config, project records and original bindings from their distinct durable copies;
then perform selected activation checks. Missing config/data leaves readiness
unresolved even if managed bytes are consistent. No speed/durability measurements
or power-loss/platform certification are claimed here.
