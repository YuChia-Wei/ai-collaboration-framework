# Proposed source development rules and adoption

This is proposed source-only policy text. U001 remains authoritative until the
owner records a concrete replacement's adoption and its effective boundary.
Portable packages and existing downstream rules do not inherit this proposal.

## Minimum useful source rules

1. Use the authorized online Issue, owning capability and bounded acceptance.
   Preserve Issue, Project, execution, integration, publication and adoption states.
   Small single-pass documentation/skill improvements may be direct with a concise
   PR record; durable multi-stage/owner-boundary work keeps a workflow.
2. Work on a dedicated branch, one tracked writer per worktree, preserving unrelated
   changes. Edit reusable product in `src/`; installed core/runtime are consumed.
   Select a current route explicitly, including remaining legacy owners.
3. Run the smallest affected checks from the pipeline decision table. A normal
   instruction edit needs content/reference review; a tool change needs focused
   behavior checks. Run native/release work only for its actual risk and authority.
4. Record actual commands, source identity, outcomes, limitations and next owner.
   Retain failures. Unknown impact blocks the affected admission; do not require a
   global history scan, all-record validation or a new evidence packet to explain it.
5. Inspect the diff and planned message, commit coherent work, then use authorized
   push/PR integration. Keep commit grammar and actual AI attribution. Current
   commit-message checking remains a small source check, not a history matrix.
6. Ordinary changes receive implementer diff inspection and maintainer acceptance
   of the PR. Authority, security, credential/publication boundaries, installation
   or recovery guarantees additionally need an independent scoped read-only review
   of the actual fixed diff, criteria and applicable source rules. Record reviewer,
   full commit, findings and disposition in the PR/workflow; no mandatory signed
   receipt, digest-rebind packet or lease platform. Changed review scope/content/
   authority needs affected review again. Never label author inspection independent.
7. After restoration, before integration read live PR head/base, **Source change
   gate** actual success, effective review blocks and any selected native/release
   results. Policy/selector changes cannot self-authorize lower review requirements.
   Missing provider facts block that claim; credentials are not a routine local test
   dependency. Close an Issue only for its accepted scope and read back merge,
   Issue and Project independently. Use `Refs` plus reason/next owner for checkpoints.
8. Published assets, support promises, active recovery records, credentials and
   external settings retain their owners. A source PR never implicitly publishes,
   installs into a target, resolves a provider defect or changes a protection.

## Staged adoption and concrete restoration proposal

| Boundary | Observable exit; remaining authority |
| --- | --- |
| Design -> coordinator selection | Reconcile #364 argv/cases and this source set. Design approval allows only the selected implementation; CI and product trials stay deferred until selected. |
| Dormant implementation -> selected local trials | New files and focused checks implemented while repository Actions stays disabled. Actual trials record failures/limits. A passed local check is not hosted success. |
| Trials -> #361 root adoption | Lesson 0.2.0 / lesson-minimal / Codex first, real target/config/store/engine/backups; later coherent source-repository 15/99 selection. Optional maintenance stays separate. No M01 without actual config-1 input. |
| Root/trial evidence -> user adoption | Present exact implemented files, commands, contexts, settings delta, scope/date of U001 narrowing and remaining release/native obligations. Ask adoption of that concrete set; no general permission question or calendar expiry. |
| Adopted set -> enable/read-back/run disposition | Coordinator enables only the adopted subset, reads settings/workflow IDs back and observes exact current-head runs. Record failed/unavailable/deferred items. Enablement and source/PR merge never mean CI passed. |

Recommended **first restoration set for later user adoption**, conditional on all
implementation/trial prerequisites above:

- Repository Actions `enabled=true`; explicit `allowed_actions=all` restores the
  recorded pre-suspension value, because current disabled response omits it.
  Present this exact setting for adoption; retain `sha_pinning_required=false`,
  `default_workflow_permissions=read`, `can_approve_pull_request_reviews=false`.
- Enable only `source-checks.yml` and `source-native.yml`, capturing their actual
  provider-assigned IDs after registration. Keep all seven legacy IDs disabled.
  No schedule, tag publication, benchmark or release credential is enabled.
  Immediately before repository enablement, read all workflow IDs/states again:
  verify the seven old IDs remain disabled and any newly registered file is in the
  adopted set. Unexpected active workflows stop restoration. Capture each setting
  write separately; repository enablement may otherwise activate an unselected file.
- Source policy requires exactly **Source change gate**, plus conditional manual
  trials/reviews. Keep live branch protection/rulesets unchanged (currently absent).
  This is maintainer-enforced admission; it does not pretend to create server-side
  enforcement. Adding a ruleset/required status protection is a separate exact owner
  choice. A future merge queue also requires a separately designed merge_group event.
- Preserve `ai-context-release` and existing credentials/settings unchanged.
  It currently has no approval protections; do not rely on it as a user-consent gate.
  #309 and any future candidate/publication enablement need separate authority.
- Stage new policy applicability under U001 until actual hosted results are available;
  if enabling or selected runs fails, preserve those failures and leave U001's
  affected remainder in force. Do not drop missing contexts or relabel deferred
  trials passed to close P7. Owner may retain a narrower checkpoint explicitly.

Ordinary checks do not revoke old published support. Before any actual legacy
support-code deletion, root route withdrawal affecting an active operation, release
workflow enablement or support-window change, identify affected versions/consumers
and active recovery data under their owners. This design does not supply that
inventory or authority.
