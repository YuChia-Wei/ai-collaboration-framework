## 問題起點

既有規劃提到「生成應用不需依賴 Framework 的工具 runtime」，容易被理解為需要另外開發、發布一個獨立重構產品。產品擁有者澄清，近期目的是 Framework 內建的簡易工具，用來降低 AI 重複生成／修改程式碼的 token，並改善產出的標準化，不希望重複建造成熟開發工具已解決的能力。

此處區分三件事：

1. **無 IDE 可用**：基本工具可在沒有 Rider 等 IDE 的環境使用。
2. **隨 Framework 交付**：工具可以是 Framework 內建能力，無需另成立產品線。
3. **生成應用不依賴工具**：工具用於開發階段；產出應用不因使用過生成或重構工具，就必須加入 Framework／Roslyn 工具套件作為建置或執行相依。應用本身明確選擇的技術相依另計。

## 產品責任的建議劃分

| 能力 | 建議責任 |
| --- | --- |
| 任務理解、規則套用、工具選擇、參數準備、修改範圍與結果審閱 | Framework 的 AI 協作能力 |
| 標準 project／file templates | 優先使用原生 dotnet new，Framework 提供預設資源與使用方式 |
| 小型 snippet | Framework 提供查詢、參數檢查與確定性展開，避免要求模型重新生成完整樣板 |
| 格式化與簡單 cleanup | 優先使用既有工具，限定檔案、規則與可觀察結果 |
| 少數基礎重構 | 評估以 Roslyn 公開能力做薄封裝，支援範圍與失敗條件清楚 |
| 較完整 IDE 語意分析與重構 | 使用者明確選擇的外部工具；依實際版本與暴露能力驗證 |
| 架構規則、專用模板、診斷、架構相關轉換 | 可由 ArchPrecept 維護專門能力，避免 Framework 複製同一套規則與實作 |

降低 token 是產品目的，尚無量測節省比例。標準化應以目標專案選擇的規則與樣式為準，不能等同強迫所有團隊使用 Framework 的單一樣式。

## 內建工具與外部擴充

內建工具應提供無 IDE 仍可使用的基本能力，不以追齊 Rider 或其他成熟 IDE 的完整功能為目標。團隊可選擇自己的模板來源、snippet 資料或替代工具。

近期建議先保持設定式選擇與清楚的呼叫／結果契約。已有 AI client 可以直接使用外部 MCP 時，Framework 可先提供能力辨識、路由與操作指引；只有確實需要轉換輸入／結果時才建立 adapter。完整 plugin host、動態 DLL 載入、marketplace、hot reload 與自製 MCP proxy 都不是本次方向自然導出的必要需求。

明確選用的外部工具未啟動、不可用或不支援該操作時，應說明限制。是否改用內建能力需有明確設定或選擇，不默默換工具。不同提供者不必具有完全相同的功能；功能缺失不能以不等價的文字取代假裝補足。

### JetBrains 整合的界線

討論中的方案是使用者自行取得符合使用條件的 Rider，開啟目標專案並啟用 MCP；Framework 提供整合方式，不將 JetBrains 專有執行檔打包成自己的引擎。

Rider 的 IDE 功能不等於全部都透過 MCP 開放。不同版本、IDE、語言與專案狀態應在實際採用時重新確認。此紀錄不證明任何特定進階操作已可呼叫，也不取代適用授權條款的確認。

參考：[Rider MCP 官方文件](https://www.jetbrains.com/help/rider/mcp-server.html)（2026-11-03 討論時查閱；文件及工具能力可能變動）。

## 若未來歸入 ArchPrecept

當工具出現獨立使用者、獨立交付需求，或較深的 .NET 架構規則與語意操作需求時，可重新評估由 ArchPrecept 承擔。這是候選發展方向，尚非拆分決議。

ArchPrecept 可考慮將 templates／snippets、analyzers、code fixes／refactorings 串成共用規則的工具組。通用 Rename 或 formatter 可以是入口能力，但不必成為主要產品價值；專用架構規則與符合契約的程式碼操作才是可能的核心。

若移交成熟實作，Framework 可改為呼叫該提供者，避免維持兩套相同重構實作。現在只需讓工具實作與 AI 操作指引分開、保持清楚入口，不必預先建立多套套件、repository 與發布流程。具體品牌、授權、預設依賴與相容性均留待當時決定。

## 跨語言演進

Framework 可共用需求理解、規則選擇、工具呼叫、變更審閱及驗證協作。語言慣例、模板、符號解析、格式化與重構由各語言的知識資源與工具提供。

.NET 是第一組深入支援的能力，不應讓 Roslyn、TFM、solution 等概念成為所有提供者的共同必填資料。共用約定只保留有實際必要的操作識別、目標、參數、結果與限制；各語言可保有專屬選項。

此為演進方向，不是多語言支援承諾。第二種語言應由真實使用情境驅動，再驗證是否需要更多共用抽象，而非預先建立完整多語言工具平台。
