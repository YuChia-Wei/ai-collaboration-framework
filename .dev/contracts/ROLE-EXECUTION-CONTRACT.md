# Provider-Neutral Role Execution Contract

This source-project contract explains how to record an actually selected role
under the [agent guardrails](AGENT-EXECUTION-GUARDRAILS-CONTRACT.md) and
[source development policy](../standards/SOURCE-DEVELOPMENT-POLICY.md).
It does not select a role, alter its package contract, or prove runtime support.

## Ownership and bounded execution

Load the selected role's current instructions and mandatory references only
when the owning skill and assigned scope make that role applicable. Keep its
purpose, inputs, permitted actions, expected output, stop conditions and named
integration owner explicit. Do not create records for unselected roles.

Direct execution remains valid when the selected role permits it and the
parent can satisfy its obligations. Delegate only within actual authority and
available runtime support. Apply the current guardrails' bounded assignment;
there is no separate proportionate-execution classifier or full execution tier
for ordinary source work. Preserve one tracked writer per worktree, permission
boundaries and immutable inputs for independent review.

A role asset or adapter entry is not an invocation. Record the actual executor
and selected model/effort separately from unknown runtime identity. Do not
silently substitute providers, privileges or spending authority. An independent
review cannot be replaced by the author's own inline review.

## Results and repairs

Use the existing task or conversation to retain the selected role, scope,
executor, actual result, evidence, limitations and integration disposition.
For independent review also record the full reviewed commit, acceptance scope,
findings and their disposition. No additional complete role-record schema,
packet or parallel ledger is required for ordinary source work.

Preserve failed or incomplete attempts. Diagnose a failure and repair or narrow
the affected work before a justified retry; follow the source policy's retry
rules and explicit owner limits. An attempt count alone does not require new
authorization. Return relevant fixes to the independent reviewer as needed.

If delegation fails, direct fallback is possible only when the same selected
role obligations and permission boundaries can still be satisfied. Record the
actual fallback and remaining gaps; never relabel the earlier child invocation
as direct execution or count an author's repair as independent verification.
If required independence or runtime capability is unavailable, report that
limitation and leave the affected acceptance unresolved.

## Historical context — NOT AN EXECUTION TRIGGER

The [earlier role execution contract](https://github.com/YuChia-Wei/ai-collaboration-framework/blob/ba28cdbc3d7001dfb101cacba5e8f71406919797/.dev/contracts/ROLE-EXECUTION-CONTRACT.md)
defines the old full role record, tier selection and numbered-attempt formats.
It preserves the meaning of existing historical records; it is not a current
ordinary-source command, record requirement or retry authorization rule.
Only an explicitly selected legacy/release obligation may choose a compatible
revision and verified tools. Do not restore unavailable tooling or migrate
historical records from this reference. Product role contracts and installed
projections remain with their separate owners.
